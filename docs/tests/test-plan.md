## 红绿循环与测试设计

1. 按实施计划依赖顺序，在目标实现分支只把当前Task对应骨架移入目标测试文件；去掉todo，连接真实模块/适配入口，补具体字节、对象、事件和assert。尚未进入的用例仍留docs骨架；最终完整门禁必须核对54个必要ID均已迁移/执行，不能以增量测试尚未写出为由永远漏掉。
2. 执行该测试，记录行为断言失败；修复工具链/导入错误之后才记录RED。语法失败、模块缺失、占位失败、TODO和skip均不是业务RED证据。
3. 最小实现一个行为，重复单项直到GREEN；再运行受影响套件。测试断言面向契约输出/资源归属/外部可见效果，不镜像内部if分支。
4. 通过实际C/WASM及浏览器原生对象的适用集成测试；再走真实用户旅程。Node的File/Blob不能替代浏览器结构化克隆及系统授权验证。
5. 修正共享解压适配须回归现有compression_test/cimbar_js_test及旧发送；配置/打包变动按实际影响复验，完整未变运行证据可复用但不能改成当前实测。

关键路径必须逐项覆盖完整/错误/截断、单在途、停止迟到回调、EOF最终帧、保存取消/写close失败/pending及真实磁盘hash。代码覆盖率若采集只用于找遗漏，不取代上述行为门禁，不凭文件行数或合成样例百分比判通过。

## 数据、隔离和执行

- D-C/D-N、A/B、V-GOOD/V-SHORT/V-LAST/V-BAD沿用验收基线，生成种子20261018；正常双输入×双类样本各3次、10轮混合会话、最终包双输入保存验证不能减少。
- 每个单元测试独立fake时钟/资源，afterEach清理；不共享已消费解压器或已detach缓冲。实际C/WASM状态会全局保留，每会话新实例；原生测试顺序敏感须隔离进程/明确初始化，不能用改模式再改回掩盖重置缺陷。
- 并行纯单元可用；真实桌面源/选择器/保存测试串行，以免抢焦点或误选来源。不得用headless自动授权参数绕过真实系统交互后称UAT通过。
- 执行命令与预期见实施计划CMD-01～10；这些工具本轮未实现。骨架本轮只做node --check语法检查，不能运行TODO后把进程退出0写成单测通过。
- 浏览器集成页必须使用真实浏览器runtime；UI工具不能控制系统对话框时，实施方安排实际人工操作并留证。无法执行保持NOT_RUN/BLOCKED，不能转交用户补本地基础验证。

## 证据、缺陷与退出

真实运行在`runs/<runId>/`另建，不改计划清单的NOT_RUN充当证据。保存测试命令、时间、执行者、构建/整套资产/profile、环境/样本、断言前后、录像/日志和外部hash。RED、修正、GREEN分别关联runId和提交，不能只留最后绿图。

功能PASS、性能目标未评定、真实现场NOT_RUN可以同时存在；它们不能互相升级。任何必要实际用例缺失或失败阻止本地“全功能通过”；0单测/TODO/skip/缺原生WASM必须阻止对应门禁。阶段5双判据和阶段6独立外审仍生效；最终product属于阶段8。
