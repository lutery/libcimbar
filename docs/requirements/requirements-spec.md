## 2. 原文摘要与用户补充

1. 项目已有 cimbar 文件编解码、原生程序及浏览器实现。
2. 原报告讨论从云桌面可见画面在本地还原文件。
3. 原报告描述的手机扫描背景存在码制证据缺口。
4. 本次直接使用本项目自带的 cimbar 发送与解码能力，不依赖历史手机扫码成功证明。
5. 用户的核心问题是手机接收不方便，需要在运行云桌面客户端的宿主机上接收。
6. 本期新增一类接收端，原有发送端、协议和其他部分尽量不改。
7. 本地实时抓屏和录像导入两种接收方式都要。
8. 实时抓屏不要求先生成录像文件；不自动增加内置录像功能。
9. 浏览器捕获可以选择独立客户端窗口，但浏览器或原生程序尚属技术方案选择。
10. 先使用实际本地环境进行同机模拟，版本和兼容范围据实记录。
11. 实施执行方先本地启动发送端和新接收端，完成全功能模拟测试。
12. 用户随后进行真实云桌面测试；本地模拟成功不代替现场通过。
13. 最终文件采用外部 SHA-256 与原文件比较。
14. 测试覆盖可压缩数据和已压缩/难压缩数据，并记录原始/编码压缩尺寸、分辨率、帧率及耗时。
15. 具体样本规模和性能阈值先实测，再确认；不引用手机性能作为桌面承诺。
16. 单文件会话、明确开始/停止、停止释放资源、干净重启和保存重试已获采纳。
17. 原名与重名行为遵循所选保存环境并文档化，不承诺跨会话续传。
18. 原报告“约 10 行修改”“5 分钟实验”“约 30 分钟搭建”不构成交付承诺。

## 3. 目标、范围与交付边界

目标：在运行云桌面客户端的宿主机上获取 cimbar 画面并还原本地文件，使日常接收不再依赖手机。

本期范围：新增宿主机接收端，提供实时抓屏和录像导入两种输入，复用现有解码、文件重建与解压能力，提供单文件接收会话、保存及必要异常处理。发送端使用原项目已有工具，优先复用原实现。系统设计需给出适用的本地启动/部署方式、录像格式与兼容矩阵；这些属于可核验的技术决策，不再要求用户从候选工具中逐项选择。

变更原则：其他部分能不改就不改。接收集成确需调整共享代码或构建/打包时，应说明必要性和影响，并验证现有行为；不据此扩展为发送端重写、协议重设计、全仓缺陷修复或大文件协议扩容。

范围外：普通 QR 兼容、全部备选兜底路径、内置录像器、云端中转/账号系统、并发多文件、跨会话续传和独立产品内哈希传输机制。完整 PWA 离线安装与全平台兼容未提出，不默认增加。

验收交付分为：可启动的新接收端及使用说明、本地全功能模拟测试证据、实测环境/容量/性能记录、供用户执行真实云桌面测试的操作与结果记录。前段编排当前只产出需求、设计与规划文档；实现、构建和运行验证属于下游实施阶段，不在本轮伪造完成。

## 4. 角色、术语与环境

| 角色/术语 | 定义 |
|---|---|
| 宿主机 | 运行云桌面客户端并显示远程画面的本地电脑；新接收端也在这台电脑上运行 |
| 发送操作者 | 在云桌面运行本项目已有发送端并显示 cimbar 动画 |
| 实施执行方 | 在本地启动发送端模拟远端画面，运行新接收端，完成全功能测试和证据交付；下游可由 Claude 接续执行 |
| 用户/现场验收人 | 使用真实云桌面执行后续验收并核对最终文件 |
| 实时抓屏 | 从所选本地窗口/显示区域持续取帧并解码，不要求保存中间录像 |
| 录像导入 | 读取已录制画面，在本地解码；格式支持清单由系统设计明确并验证 |
| cimbar 模式 | B/Bu/Bm/4C 等编码参数；首轮支持矩阵由设计列出，不把默认模式等同于全模式支持 |
| 正确性 | 已保存接收文件的外部 SHA-256 与同一发送原文件一致 |

首轮按实际本地 Windows 环境建立基线；记录系统、浏览器或原生运行时、发送工具、显示分辨率和缩放。未知版本、容量与性能采用“先测量，再确认支持范围”的已批准策略，不假设所有 Windows 或浏览器版本均兼容。

## 5. 功能需求

### FR-001：实时抓屏接收

- 来源：USR-01 Q-001/Q-004；验收：AC-001、AC-002、AC-006、AC-007。
- 触发/前置：操作者开始实时接收，发送端正在目标窗口显示 cimbar 动画，运行环境具备所需捕获权限。
- 主流程：选择捕获源 → 获取画面 → 向解码器提交有效帧 → 更新接收状态。
- 分支/异常：取消或拒绝选择、无有效画面、黑屏、源中断时显示可理解状态，允许重新开始，不得显示文件接收成功。
- 数据/权限：读取选定画面；按系统或浏览器机制获取授权，不默认读取其他输入源或保存原始录像。

### FR-002：解码并重建原文件

- 来源：SRC-01、USR-01 Q-002/Q-004；验收：AC-002、AC-004、AC-008。
- 前置：现有项目发送端生成兼容模式数据，接收足量有效数据。
- 主流程：逐帧解码 → 累积文件数据 → 重建并解压 → 产生完整输出。
- 分支/异常：损坏帧、无有效帧、模式不匹配或数据不足不得成为成功结果；报告状态并允许停止和重新开始。录像到 EOF 仍不完整时应结束处理并报告未完成，不能无限空转。
- 数据：复用现有协议和解码能力，不新增协议字段或自动拆包要求。

### FR-003：本地保存与失败重试

- 来源：USR-01 Q-005/Q-006；验收：AC-003、AC-009。
- 前置：完整文件已重建。
- 主流程：提供保存入口 → 操作者取得本地文件；保留原文件名，重名行为遵循选定保存环境并在说明中写明。
- 分支/异常：保存取消或写入失败时显示状态并可重试保存，不应要求重新接收仍在本会话中的已重建文件；会话停止/重置或程序关闭后的保留不作承诺。
- 权限：使用当前进程/浏览器可用的保存机制，不承诺任意目录静默写入。

### FR-004：外部文件一致性验收

- 来源：USR-01 Q-005；验收：AC-004、AC-010、AC-011。
- 前置：发送原文件和最终已保存文件均可取得。
- 主流程：外部计算两侧 SHA-256，记录文件标识、字节数与哈希，逐项比对。
- 异常：哈希不同为 FAIL，任一侧证据缺失为未完成验收，未执行为 NOT RUN。
- 边界：这是验收工作流，不要求产品向协议新增哈希字段或上传文件。

### FR-005：录像导入接收

- 来源：USR-01 Q-001；验收：AC-014、AC-008。
- 触发/前置：操作者选取系统设计明确支持的视频文件，其中包含本项目发送端动画。
- 主流程：校验输入可读取 → 按帧输入解码链路 → 重建文件 → 保存。
- 分支/异常：取消选取、不支持或损坏的视频、无有效码帧以及 EOF 时数据不足均需给出结果并可重新选择/开始；失败输入不能沿用旧会话成功状态。
- 数据：读取已有录像；不要求集成录制工具。支持的容器/编码组合在设计和本地测试中固定。

### FR-006：单文件会话与资源释放

- 来源：USR-01 Q-006；验收：AC-006、AC-007。
- 主流程：一次会话先接收一个文件；操作者可明确开始、停止；停止时释放捕获源、视频处理等会话资源；再次开始建立干净会话。
- 分支/异常：旧任务迟到结果不得串入新会话；失败显示可见错误；不承诺跨会话保留解码进度。
- 数据：会话内暂存接收与重建数据，按停止/重置边界清理。单次失败后的保存重试按 FR-003 处理。

## 7. 用户流程

实时：在云桌面启动原发送端 → 宿主机启动新接收端 → 开始并选择画面 → 解码和重建 → 本地保存 → 外部 SHA-256 核对。

录像：准备含发送动画的视频 → 宿主机导入录像 → 解码到完成或 EOF → 完成后保存 → 外部 SHA-256 核对。未完整重建就到 EOF 时返回未完成结果。

异常：取消/拒绝输入或捕获中断 → 显示状态 → 可重新开始；停止 → 释放资源 → 再次开始时清理旧进度；保存失败/取消 → 保留本会话可重试结果 → 再次保存。

本地验证：在同一台本地电脑运行现有发送端模拟远端显示，同时运行新接收端，分别通过真实抓屏和录像输入验证以上流程。直接将 PNG 或内存字节喂给解码器的单测不能代替这项模拟 E2E。

## 8. 数据与集成

输入：现有 cimbar 发送端画面、已有录像；输出：最终还原文件和测试证据。复用仓库现有解码、喷泉重建与 zstd 解压能力，不引入数据库或传输协议扩展。

浏览器/WASM 或原生接收程序、捕获 API、视频读取方式、HTTP 服务/运行时和打包方式在系统设计阶段选定并给出依据。不能仅凭原报告“零构建”建议冻结架构。若复用现成 WASM，应核验版本/导出接口与源代码一致；如需构建，应说明必要性。

本地模拟发送工具优先使用仓库已有且能运行的发送入口；真实云桌面继续复用项目发送端。确切入口、模式和版本作为测试环境证据记录，避免强迫用户提前选择工程实现。

## 10. 静态核对与风险

- `web/recv.html:434`～`:435` 在主线程 WASM 初始化后自动调用摄像头初始化，与原报告声称的“开始按钮”不同；设计屏幕捕获入口时需重新核对。
- `web/recv.js:244` 当前使用摄像头输入；`web/zstd.js` 有 Blob 下载路径。代码存在不等于新抓屏/录像链路已可运行。
