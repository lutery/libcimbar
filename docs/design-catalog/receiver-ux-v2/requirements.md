# 设计输入与约束

输入：[已确认需求](../../requirements/receiver-ux-v2/requirements-spec.md)、[问题与回答](../../requirements/receiver-ux-v2/open-questions.md)、[实际代码可行性](../../requirements/receiver-ux-v2/feasibility.md)。基线`9e4fbc46965de42b9b0097ad80c607d71c7303f0`。

## 目标、角色与范围

宿主机使用者需要知道是否正在接收、是否有进展及下一步操作。云桌面发送端保持原行为。实时抓屏、录像导入两个独立按钮均保留；接收时仍按现有互锁禁用启动按钮，停止与保存权限来自现有会话状态。

FR-UX-001～005落实为：中文反馈、时长、含义明确的近期识别速率、可判定时的码流重建估计、双输入入口。NFR-UX-001～005要求真实、有界、兼容、可访问、会话隔离。AC-015～024逐项追踪见[架构](architecture.md)。

## 架构约束

1. 原业务状态机仍是唯一会话状态权威。新增的是观察状态和界面投影，不把Receiving拆成新的业务状态枚举。
2. 单在途、严格EOF、产物预算、停止收敛、保存write+close成功判据、旧会话隔离均保持。
3. 原发送协议及C++/WASM算法不改。已有report为可选观测能力，缺失/格式异常不能破坏正常解码。
4. 指标时钟以主线程单调时钟为准，跨Worker不比较绝对时钟。后台/休眠后按当前时钟重算，而非累计tick次数。
5. 原receiver-v1外部schema保持不变；新的内部UX遥测与既有stats分离。阶段2.5定义内部消息和展示快照的明确边界，不能直接向严格v1对象加字段。
6. 核心按钮、系统选择器与保存流程保持用户激活要求；界面计时器只能重绘，不能触发抓屏、导入、保存或重建。
7. 原始field证据及用户成功反馈分别保留，本次原型不调用屏幕/文件权限，不生成验收PASS。

## 已决策

- 用户Q-001：按照推荐执行；后续“其余的没问题了”，授权进入设计。
- 两个入口保留，双输入都增加反馈；不是入口替换。
- 中文、深色背景/青色主色、现有系统字体沿用已有UI，新增信息层级。
- 进度是码流块收集参考，识别速率包含协议/冗余数据；不提供无依据的文件剩余字节或倒计时。

## Hotspots与验证项（无待用户回答的需求问题）

| 编号 | 风险/不确定项 | 本阶段处理 | 后续证明 |
|---|---|---|---|
| H-01 | 部署资产可能无report导出或报告不可解析 | 可选能力降级；只在正确阶段读report | 2.5契约负例、阶段5真实资产正负例 |
| H-02 | 多活动流无ID、报告顺序不稳定 | 多流或有效比例回退后，本会话锁定不可判定，直到新会话；不取max/sum | 多流/切换/延迟回调回归与真实输入 |
| H-03 | 新遥测与重绘开销可能影响解码 | 有界采样，重绘至多4次/秒，原调度不变 | 4.x冻结同输入A/B方法，5实测记录吞吐及尾延迟 |
| H-04 | 实际窗口大小与中文文案可读性 | 桌面和窄窗口原型核对；文字状态与键盘焦点 | 原型可用性检查与阶段5真实窗口操作 |

刷新/窗口/提示阈值是本设计的初始参数，不称性能SLA；变更须同步设计与测试记录。没有会改变本轮范围或成功判据的未决P0。
