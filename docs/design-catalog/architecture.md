# 宿主机接收端架构与决策

2026-10-18；基线 `84e7a1a`。本文件为系统设计，不是实现或运行验收。

## 1. 方案决策

采用独立的本地浏览器接收应用：在宿主机打开新接收页面，浏览器负责捕获远程桌面客户端窗口/显示器或读取录像，专用 Worker 使用现有 WASM 完成解码、重建与解压，页面负责状态和保存。交付为本地静态资源与启动说明/入口；本阶段不承诺原生 EXE 安装包。

这满足“在运行云桌面的宿主机上跑的程序”，并最小化原项目变动。选择依据是已有 `cimbard_*` 导出和浏览器 WASM Worker 先例，而不是报告里的“约 10 行修改”。原生接收扩展同样可行，但需额外接入 Windows 捕获与原生视频/GUI 生命周期，本期不同时开发两套。实际能力以本地模拟结果为准。

首轮设计以 Windows 桌面 Edge 为主、Chrome 为兼容验证候选；Firefox/Safari/移动端不进入首轮矩阵。只读版本盘点发现本机 Windows build 22631、Edge 155.0.4283.45、Chrome 155.0.8059.84。这里只证明文件/版本存在，未启动浏览器验证 API 或功能。

## 2. 模块边界

| 模块 | 职责 | 不承担的职责 |
|---|---|---|
| 接收界面 | 实时/录像入口、模式、开始/停止、预览、状态、保存动作 | 编解码协议、隐式后台抓屏 |
| 会话协调器 | 唯一活动会话、身份/状态检查、启动和停止、EOF 屏障、资源所有权 | 持久化续传、并发多文件 |
| 实时输入 | 系统源选择、捕获流、源结束/尺寸变化观察、自然尺寸画面 | 给浏览器预选来源、内置录制 |
| 录像输入 | 本地文件、媒体能力/元数据检查、播放与受控取帧、EOF 信号 | 通用视频转码、所有容器解码 |
| 帧调度 | 源时间戳与尺寸、固定上限的在途帧、忙碌背压、结束排空 | 无限排队、把重复图像当新数据 |
| 解码 Worker | 每会话一个新 WASM 实例；scan/fountain/decompress、状态与文件产物输出 | 系统捕获权限、磁盘保存 |
| 产物与保存 | 不可变 Blob、建议原名、显式保存、关闭结果、会话内重试 | 自动证明文件 SHA-256、跨会话保留 |
| 验证证据 | 测量/运行版本/AC 结果与两侧哈希 | 用本地模拟替代现场验收 |

概念数据模型仅描述内存对象与测试记录，不引入数据库或服务器业务 API。详细模块契约和错误码在阶段 2.5 冻结。

## 3. 与现有项目的复用边界

| 现有能力 | 当前源码事实 | 新接收端如何复用 |
|---|---|---|
| 本项目发送端 | `src/exe/cimbar_send/send.cpp` 及 `web/index.html` | 不需发送端改造；本地模拟选能运行的已有发送入口，记录版本/模式 |
| 像素解码 | `cimbard_scan_extract_decode` 支持 RGBA 路径 | 使用自然宽高的 RGBA 帧，不复制摄像头 constraints 或既有帧调度逻辑 |
| 喷泉重建 | `cimbard_fountain_decode` 返回 int64 完成 id | 单 Worker 内处理，正值取有效文件标识；保持现有 BigInt ABI，不把截断前结果作 Number 比较 |
| 文件名/解压 | `cimbard_get_filename`、`cimbard_decompress_read` | 在同一实例依次取名/读取，复制堆数据后形成 Blob；负值为失败，只有明确正常结束才能标记产物就绪 |
| 配置 | `cimbard_configure_decode` 仅模式变化时重置部分状态 | 不用反复设置同一模式模拟 reset；每新会话替换 Worker/WASM |
| 发布与构建 | `src/lib/cimbar_js/CMakeLists.txt` 已列接收导出；`web/` 无生成 JS/WASM | 优先成对复用已核验产物；不匹配时走原构建能力，不重写 C++ 解码协议 |

新页面与新 Worker 独立于 `web/recv.html`、`web/recv.js` 和原摄像头 Worker。原脚本可作为参考，不能因“复用”而保留其自动启动、全局旧状态、主线程重建或保存不可确认等行为。固定堆、文件名缓冲与有符号返回必须按接口和实际产物验证。

## 4. 会话与异步一致性

每次开始产生新会话身份，并创建新 Worker/WASM；会话中固定输入类型和模式。B 为必须验证的基线模式；Bu/Bm/4C 为兼容验证候选，界面只发布实际通过的支持范围。自动探测不是本期前置能力，不能在积累数据时轮换模式并清空已有重建状态。

输入帧、初始化结果、捕获授权返回、录像事件、Worker 消息和保存结果都与所属会话绑定。停止先使该会话失效、禁用取帧，然后关闭输入、取消帧回调/等待、终止 Worker 并清除产物；迟到授权若返回了流，应立即停止其 tracks，不能遗留抓屏。新会话不接纳旧消息。

输入选择取消与拒绝同样不算成功；无法区分黑屏、没有码或压缩损伤时提示“尚未检测到有效数据”，不编造原因。首个文件完整重建后停止输入，不继续接收第二文件。Worker 解压失败不产生可保存“完整文件”。

保存写入期间禁止新建会话，避免旧写入结果与新会话串联；停止/关闭请求进入清理，尽可能取消在途写入并等待其完成或失败，再释放产物。若写入在停止竞态中已提交，已保存文件不回滚或删除，界面如实报告。无需新增删除用户文件的操作。

## 5. 实时抓屏与录像的不同策略

实时：从点击事件直接发起系统选择，不能先等待异步 Worker 初始化再调用捕获。能力检查/资源预热可在用户操作前完成；捕获流与 Worker 均就绪后才开始取帧，任一失败都清理另一方。只请求视频，不请求音频，不使用 `min`/`exact` 约束。选定源由用户决定，程序不能保证选择器只显示远程窗口。[MDN：getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)

读取自然视频尺寸，预览 CSS 缩放不改变送入解码的像素尺寸。使用 Canvas RGBA 作为统一帧表示，避免把现有 NV12/I420 分支当所有浏览器保证。初版设计为单在途帧且无待处理队列；实时忙碌时丢弃新采样并计数，不阻塞 UI、不积压无限帧。

录像：本地文件形成受会话管理的 Object URL，媒体元数据和实际解码能力检查成功后播放。首轮验证 MP4/H.264 与 WebM/VP8 两种组合，扩展名/MIME 和 `canPlayType` 仅作预检，不能代替实际解码。失败组合不进入已支持清单，具体编码配置由测试计划记录。

录像采用受控播放：获取一次呈现帧后暂停/等待该帧处理，再恢复处理后续帧；必要时降低播放速率并记录。帧回调是尽力而为的呈现通知，不保证逐帧无遗漏；使用媒体时间/呈现帧计数去重和测量遗漏，不能把高吞吐依赖建立在“每帧必到”上。格式/信号验证必须包含真实录像 E2E。[MDN：requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

`ended` 仅表示输入结束，不能立即判定传输失败；先锁存 EOF、停取新帧，若当前最终呈现帧尚未提交，在有限槽空闲时补采一次，再排空已提交工作。不能等待结束后可能不再触发的帧回调；待 Worker 给出重建/解压结果后才判成功或“不完整”。EOF 后不循环重放、不无限 read；无可用数据或视频错误均允许重新导入。源停止与用户主动停止采用不同事件，主动停止不必等数据完成。

若首轮浏览器取帧策略无法对支持格式稳定通过，应在本接收端内改进受控抽帧并记录设计变更；不得悄悄宣称支持，也不自动引入原生接收端或修改发送协议。

## 6. 内存与生命周期

只有一个解码实例与一个在途像素缓冲。当前构建设置 `TOTAL_MEMORY=134217728`，不据此承诺最大可接收文件大小；帧像素、OpenCV 中间图、压缩输入、解压输出和 Blob 会共同占用内存。

按实际像素尺寸预检分配预算；OOM/无效尺寸、解压错误或产物超预算时停止并给出状态，不静默缩放、截断或输出半文件。初期预算与限制通过 V-002/V-003 测量冻结；压缩后协议上限与宿主内存上限分别记录。不自动处理协议越界或压缩炸弹到无限分配。

重建完成后的 Blob 转移至页面并确认接收后，可终止解码 Worker，释放 WASM；当前会话仍保有产物以保存/重试。停止/重置/页面退出清理所有 tracks、媒体 src、帧回调、Object URLs、Worker 和 Blob 引用。主动 `track.stop()` 不等待浏览器再发 `ended` 才清理。[MDN：停止捕获](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Capture_API/Using_Screen_Capture)

## 7. 保存语义

首轮基线使用显式“保存文件”动作调用系统保存选择器；不从 Worker 完成回调自动弹出。新接收端运行前检查 `showSaveFilePicker` 能力，缺少时说明当前环境不在已验证保存基线内，不自动降级成无法确认完成的下载路径。

重建产物为不可变 Blob。选择器使用发送文件名的安全 basename 作为建议，缺失时用回退名并标明；重名覆盖由系统选择器让用户决定。只有创建写入流、写入及 `close` 全部成功，才标记“保存完成”。选择取消/权限或 IO 错误时保留 Blob，可重新点击保存；不会重新调用已经消耗过的 WASM 解压器。[MDN：showSaveFilePicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker)、[createWritable](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createWritable)

“保存完成”只指浏览器写入链路完成；是否与原文件一致仍由外部 SHA-256 核验。首轮不新增程序内上传或哈希协议。

## 8. 本地装配与最小改动面

建议新增一个独立 `web/desktop-recv/` 源目录，存放接收页、会话/输入/保存协调逻辑和新解码 Worker；最终文件拆分由后续计划给出。需要的 `cimbar_js.js`/`.wasm` 在装配目录成对提供，保留来源版本和校验值。Worker 与 WASM 加载器使用同一明确的资源基地址，装配检查必须覆盖两级加载实际解析路径，不能假设 Worker 子目录下存在全部二进制。不得用不含解码导出的 asm.js 单文件代替。

本地入口通过仅绑定回环地址的静态服务打开，固定独立 origin/端口与资源根，采用同源相对资源地址；不使用 `file://`，不要求用户部署公网服务。启动入口需提供运行时检查、端口占用提示和打开页面说明；具体脚本在实施阶段编写。浏览器对回环来源的安全上下文、抓屏和保存 API 仍以运行时能力检查为准。[MDN：可信来源](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)

新接收端不注册 Service Worker，也不复用原 PWA 的缓存清单/根路径；避免继承已有打包漏项和缓存覆盖。装配不得修改原发送页面的 URL/资源或需要发送端升级。必要新增测试和独立打包/启动文件属于接收端配套，不能把“最小改动”解释为零验证。

## 9. 验证分层与全部 AC 落点

| AC | 设计落点 | 所需证据 |
|---|---|---|
| AC-001 | 实时输入、用户选择、自然尺寸帧 | 本地实际窗口抓取记录，不能只注入像素 |
| AC-002 | 单 Worker 重建/解压、正常结束判定 | 有效传输和不完整输入对照 |
| AC-003 | 显式保存及正常 close | 最终文件、文件名/重名行为 |
| AC-004 | 外部 SHA-256 | 发送原文与最终保存文件的哈希 |
| AC-005 | 文档/单元/本地/现场结果分层 | 每项运行时间、环境与 PASS/FAIL/NOT RUN |
| AC-006 | 权限取消、源中断、无有效数据 | 真实交互与可控故障各自标明；没有现场故障证据不得假称已测 |
| AC-007 | 全新实例、身份校验、统一清理 | 停止/重启及迟到返回、资源释放记录 |
| AC-008 | 视频错误和 EOF 屏障 | 无效格式/损坏/不足数据、最后帧仍可完成的用例 |
| AC-009 | Blob 与保存尝试分离 | 取消/权限失败/写入失败后重试，字节不变 |
| AC-010 | 同机原发送端与新接收端真实双输入 | 全流程及异常用例映射，压缩/难压缩数据 |
| AC-011 | 用户真实云桌面测试 | 单列现场环境、输入、哈希和结果 |
| AC-012 | 帧/传输/保存时点和规模测量 | 原始/压缩尺寸、模式、分辨率/缩放、源/处理帧率、耗时、重复次数 |
| AC-013 | 独立接收目录与已验证二进制来源 | 改动面、现有发送可用/协议兼容证明 |
| AC-014 | 录像输入成功路径 | 每个发布支持的容器/编码组合的真实视频解码和哈希 |

本地模拟使用发送端窗口真实显示动画；先验证其原生入口或已有浏览器发送页能运行，再运行接收端。若用浏览器发送页，应在独立窗口显示并选择发送窗口作为捕获源，避免选择当前接收页面产生递归画面。录像样本从这一真实窗口录制，记录采集参数；用 PNG/内存直接注入只算单元或集成，不能替代双输入 E2E。屏幕授权选择、权限和保存对话框涉及桌面交互，自动化无法覆盖的部分必须列 NOT RUN 并安排实际交互补测，不用 mocked API 掩盖。

计时分别记录初始化、源可用/首次帧、首个有效数据、重建完成、保存完成；录像另记媒体时长与处理时长。无已确认性能阈值时，功能/哈希可通过，性能只能报告测量值。用户真实云桌面结果与本地模拟独立，不能因模拟通过改写现场状态。

当前设计 QA 与产品测试分开：源码/文档核对已执行，WASM 装配验证、本地全功能模拟、现场验收和性能容量测量均 NOT RUN。

## 10. 阶段决策与后续

SD-001：独立浏览器应用作为本期接收端；SD-002：双输入汇入同一单实例解码链路；SD-003：新 Worker/WASM 隔离每个会话；SD-004：Blob 与保存尝试分离；SD-005：EOF 排空且无无限自动循环；SD-006：独立本地 origin、无 PWA 缓存耦合；SD-007：先本地实际窗口 E2E，再用户现场验收。

阶段 2.5 细化补充 SD-008：严格正常解压结束不能只靠“读到 0 字节”推断。当前导出忽略底层 write_once 返回，压缩帧完成状态也未明确保留；装配必须证明损坏/截断不假成功。必要时只修正现有解压适配的错误/结束判据并重建，保持正常 ABI、发送端和传输协议兼容。详见 [模块契约](module-contract-error-matrix.md)，不再承诺原预编译 WASM 无条件直接复用。

这些是本阶段设计决定，不把具体框架/原生安装器额外加入需求。热点见 [requirements.md](requirements.md)，源码和文档证据见 [sources.md](sources.md)。下一步可进入模块职责/接口 schema/错误矩阵细化，或由用户选择跳过后进入任务规划。
